# سَنَد — معمارية الأمان (منصة مبرمجة من الصفر)

> **المبدأ:** ما في نظام آمن 100%. الهدف إنه الاختراق يكون صعب جداً، وإذا صار يكون محدود الضرر، ونكتشفه بسرعة، ونقدر نرجع منه.
> هاي الوثيقة هي المرجع. أي ميزة جديدة لازم تمر على البنود المعنية فيها قبل ما تنزل.

---

## 0. التقنيات (Stack) — ليش هيك
| الطبقة | الاختيار | السبب الأمني |
|---|---|---|
| Backend | **Django 5 (Python)** | حماية جاهزة ومجربة: CSRF، ORM ضد SQL Injection، Auto-escaping ضد XSS، و Argon2 لكلمات السر |
| قاعدة البيانات | **PostgreSQL** | Transactions و Row locking للأرصدة، و Triggers لمنع تعديل الدفتر |
| المهام بالخلفية | **Celery + Redis** | الاتصال بالموردين من Worker معزول، مش من سيرفر الويب |
| الواجهة | HTML من السيرفر + JS بسيط (المرحلة 3) | سطح هجوم صغير، و CSP صارم بدون inline scripts |
| الحماية الأمامية | **Cloudflare** | WAF، و DDoS، و Bot management، و Rate limiting |

---

## 1. البنية التحتية
- [ ] **السيرفر الأصلي مخفي:** الـ Firewall بيقبل اتصالات بس من IPs تبعت Cloudflare، وأي حدا بيوصل للـ IP مباشرة بينرفض.
- [ ] **لوحة الإدارة على دومين فرعي منفصل** (مثلاً `ops.`) ورا **Cloudflare Access (Zero Trust)**: ما بتفتح صفحة الدخول إلا لإيميلات وأجهزة محددة.
- [ ] **قاعدة البيانات و Redis** على شبكة داخلية، ومفيش أي Port مفتوح للإنترنت.
- [ ] **SSH:** مفاتيح فقط، بدون root وبدون كلمات سر، مع Fail2ban ومنفذ مقيّد بـ IP أو VPN (Tailscale/WireGuard).
- [ ] **تحديثات أمنية تلقائية** للنظام (unattended-upgrades).
- [ ] **الأسرار** (مفاتيح API الموردين، Django SECRET_KEY، كلمات سر DB) بمتغيرات بيئة أو Secret manager، **مش بالكود ولا بـ Git أبداً**، مع Secret scanning على المستودع.
- [ ] **بيئات منفصلة:** Production و Staging. التجارب ما بتصير على الحقيقي.
- [ ] **نسخ احتياطي:** يومي، مشفّر، خارج السيرفر (مكان ثاني)، مع **تجربة استرجاع فعلية كل شهر**. نسخة احتياطية ما انجربت كأنها مش موجودة.

## 2. الهيدرز والمتصفح
- [ ] `Content-Security-Policy`: `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; font-src 'self'; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`
  - الواجهة مبنية من الأساس بدون inline scripts أو styles عشان هالسياسة تشتغل. **الخطوط بتنستضاف عنا** بدل Google Fonts.
- [ ] `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload` + التسجيل بـ HSTS preload
- [ ] `X-Content-Type-Options: nosniff` · `Referrer-Policy: strict-origin-when-cross-origin` · `Permissions-Policy` يقفل الكاميرا والمايك والموقع
- [ ] الكوكيز: `Secure; HttpOnly; SameSite=Lax`، و`__Host-` prefix لكوكي الجلسة
- [ ] TLS 1.2+ فقط · تقييم A+ على SSL Labs و securityheaders.com

## 3. الحسابات وتسجيل الدخول
- [ ] **كلمات السر:** Argon2id، و12 حرف كحد أدنى، ورفض كلمات السر المسرّبة (Have I Been Pwned بطريقة k-anonymity).
- [ ] **2FA (TOTP):** **إجباري للأدمن والموظفين**، وإجباري للزبون لما رصيده يتجاوز [$100] أو قبل ما يفعّل الـ API. مع رموز احتياطية مشفّرة.
- [ ] **Passkeys (WebAuthn):** دخول ببصمة الجهاز. أقوى خيار ضد التصيّد (Phishing).
- [ ] **الأدمن:** مفتاح أمان عتادي (YubiKey) كعامل ثاني، مش بس تطبيق.
- [ ] **Rate limiting** على الدخول واسترجاع كلمة السر والتسجيل (حسب IP وحسب الحساب)، مع قفل تدريجي وCAPTCHA (Cloudflare Turnstile) بعد محاولات فاشلة.
- [ ] **الجلسات:** تتجدد بعد الدخول، وبتنتهي بعد خمول، مع قائمة أجهزة نشطة وزر «اقفل كل الجلسات».
- [ ] **إعادة تحقق (Re-auth)** قبل العمليات الحساسة: تغيير الإيميل أو كلمة السر، تعطيل 2FA، إنشاء مفتاح API.
- [ ] **إشعار فوري (واتساب + إيميل)** عند: دخول من جهاز جديد، تغيير بيانات أمنية، شحن، أو تعديل رصيد يدوي.
- [ ] رسائل الخطأ ما بتكشف إذا الإيميل مسجل أو لا.

## 4. المال: الرصيد والدفتر ⭐ (أهم قسم)
- [ ] **دفتر حسابات بالقيد المزدوج (Double-entry ledger):** كل حركة (شحن، خصم طلب، استرجاع، تعديل) بتنسجّل كقيد. **الرصيد بينحسب من القيود**، مش رقم بيتعدل.
- [ ] **الدفتر Append-only:** Trigger على مستوى قاعدة البيانات بيمنع UPDATE و DELETE على جدول القيود. أي تصحيح بيكون قيد عكسي بسبب مكتوب.
- [ ] **المبالغ بوحدات صحيحة** (سنتات) أو `Decimal`، **وممنوع float**.
- [ ] **كل عملية مالية بـ Transaction واحدة** مع `SELECT … FOR UPDATE` على محفظة الزبون، عشان طلبين بنفس اللحظة ما يصرفوا نفس الرصيد (Race condition).
- [ ] **Idempotency key** لكل طلب وكل شحنة: الضغط مرتين أو إعادة إرسال الطلب ما بيخصم مرتين.
- [ ] **السعر والرصيد بيتحسبوا على السيرفر لحظة التنفيذ.** أي سعر جاي من المتصفح بينتجاهل.
- [ ] **مطابقة يومية تلقائية (Reconciliation):** مجموع الدفتر = مجموع الأرصدة، والطلبات المرسلة للمورد = خصومات المورد. أي فرق بيطلق تنبيه فوري.
- [ ] **حدود (Limits):** حد أقصى للطلب الواحد، وسقف يومي للحسابات الجديدة، وتجميد تلقائي عند نشاط غير طبيعي.
- [ ] **ما في سحب رصيد أوتوماتيك.** أي إرجاع فلوس بيصير يدوي وبموافقة.

## 5. الشحن والدفع
- [ ] **ممنوع اعتماد شحنة على صورة إثبات فقط.** الصور بتتزوّر بسهولة. الاعتماد بعد التأكد من وصول المبلغ فعلاً بتطبيق البنك أو المحفظة.
- [ ] **رقم مرجع فريد لكل طلب شحن** (`SND-TOPUP-XXXX`) لازم ينكتب بالحوالة.
- [ ] **USDT:** المرحلة الأولى عبر Binance Pay Merchant API مع **التحقق من توقيع الـ Webhook**. المرحلة الثانية عناوين إيداع خاصة لكل زبون (HD wallet، والمفتاح الخاص **مش على السيرفر**) مع التأكد من التحويل على البلوك تشين.
- [ ] **مبدأ الأربع عيون:** أي شحنة يدوية فوق [$500] أو أي تعديل رصيد يدوي بيحتاج موافقة شخصين، أو تأكيد ثاني بمفتاح عتادي.
- [ ] كل اعتماد بينسجل: مين اعتمد، ومتى، ومن أي IP، ومرجع العملية.

## 6. الاتصال بالموردين (Iraq Server وغيره)
- [ ] مفاتيح API الموردين **مشفّرة بقاعدة البيانات** (Field-level encryption) والمفتاح الرئيسي برا الـ DB.
- [ ] الاتصال بيطلع **من Worker معزول فقط**، مع طلب **تقييد مفتاحنا على IP السيرفر** من جهة Iraq Server.
- [ ] Timeouts و Retries محسوبة. الطلب المعلّق ما بيعتبر فاشل، بيضل «قيد التحقق» لحد ما المورد يأكد.
- [ ] **الاسترجاع للزبون بيصير فقط لما المورد يأكد رسمياً إنه الطلب انرفض.** هيك ما بيصير عنا ربح أو خسارة وهمية.
- [ ] **رصيدنا عند المورد = شغل أسبوع فقط.** إذا انخترق حساب المورد، الخسارة محدودة.
- [ ] ردود المورد بتتعامل كبيانات غير موثوقة: بتتفحص، وبتتعرض للزبون بدون HTML.

## 7. التطبيق نفسه (OWASP Top 10)
- [ ] **صلاحيات على كل طلب (IDOR):** كل Query بتتفلتر على الزبون صاحب الجلسة. الزبون ما بيقدر يشوف طلب أو فاتورة غيره بتغيير رقم بالرابط.
- [ ] **التحقق من المدخلات:** IMEI بخوارزمية Luhn وطول 15، والإيميلات، والمبالغ ضمن حدود. Allowlist مش Blocklist.
- [ ] **رفع الملفات (إثبات الدفع):** فحص النوع الحقيقي (مش الامتداد)، وحد 5MB، **وإعادة ترميز الصور** (بتمسح أي كود مخفي)، وتخزين برا مجلد الويب بـ Bucket خاص بروابط موقّعة مؤقتة، وفحص فيروسات (ClamAV).
- [ ] **API الزبائن:** المفاتيح مخزنة كـ hash، وبتنعرض مرة وحدة بس، ومقيّدة بـ IP، مع صلاحيات محددة و Rate limit لكل مفتاح.
- [ ] ما في أي HTML من المستخدم بيتعرض. كل النصوص Escaped.
- [ ] رسائل الأخطاء للمستخدم عامة، والتفاصيل بالسجلات بس. `DEBUG=False` دائماً على الإنتاج.

## 8. لوحة الإدارة
- [ ] **صلاحيات حسب الدور (RBAC):** دعم فني (يشوف طلبات فقط)، ومحاسب (يعتمد شحنات ضمن سقف)، و Owner (فادي).
- [ ] **Audit log ثابت** لكل عملية إدارية، ما بينمسح.
- [ ] ممنوع تعديل الأرصدة من قاعدة البيانات مباشرة. كل تعديل بيمر من الواجهة كقيد مع سبب.
- [ ] تنبيه فوري لفادي على أي تعديل رصيد يدوي أو تغيير صلاحيات.

## 9. المراقبة والإنذار
- [ ] تتبع الأخطاء (Sentry) + مراقبة التوفر (Uptime) + سجلات مركزية بتنحفظ 90 يوم.
- [ ] **تنبيهات فورية على تيليجرام أو واتساب** عند:
  - محاولات دخول فاشلة كثيرة أو دخول أدمن من مكان جديد
  - فرق بالمطابقة اليومية
  - نزول رصيدنا عند المورد تحت حد معين، أو هبوط مفاجئ فيه
  - ارتفاع غير طبيعي بالطلبات من حساب واحد
- [ ] **خطة الطوارئ (Incident response):** زر «وضع الصيانة» بيوقف الطلبات والشحن فوراً، مع خطوات مكتوبة: تدوير كل المفاتيح، وقفل الجلسات، والتواصل مع المورد، وإبلاغ الزبائن.

## 10. عملية التطوير
- [ ] Code review لكل تعديل بيمس الفلوس أو الصلاحيات.
- [ ] فحص تلقائي بكل commit: `pip-audit` و Dependabot للمكتبات، و `bandit` و `semgrep` للكود، و Secret scanning.
- [ ] **اختبارات آلية للدفتر:** طلبات متزامنة، وضغط مرتين، واسترجاع مكرر، ومبالغ سالبة.
- [ ] **فحص اختراق خارجي (Pentest) من شركة مستقلة قبل الإطلاق** وبعد كل تغيير كبير. هاد مش اختياري لنظام بيمسك فلوس.
- [ ] بعد الإطلاق: برنامج إبلاغ عن ثغرات (security.txt + مكافأة بسيطة).

## 11. الإنسان (أضعف حلقة)
- [ ] فريق سَنَد **ما بيطلب** كلمة سر أو رمز تحقق أبداً، ومكتوب هالشي بكل مكان بالموقع.
- [ ] رقم واتساب الدعم موثّق (Business verified)، والزبائن بيعرفوه.
- [ ] أي طلب تغيير إيميل أو رقم من الدعم بيحتاج تحقق هوية، ومهلة 24 ساعة، وإشعار للبيانات القديمة.
- [ ] جهاز فادي الإداري: تشفير القرص، ومدير كلمات سر، و 2FA على الإيميل والدومين (الدومين بقفل Registrar lock).

## شروط قبل الإطلاق (Go-live gate)
ما بنستلم أول دولار من زبون حقيقي قبل ما يتحقق كل هاد:
1. كل بنود القسم 4 (المال) مطبقة ومختبرة.
2. 2FA إجباري على كل حسابات الإدارة.
3. نسخ احتياطي مجرّب باسترجاع حقيقي.
4. Pentest خارجي بدون ثغرات حرجة أو عالية مفتوحة.
5. المراقبة والتنبيهات شغالة.
6. Soft launch مع 10–20 محل موثوق بسقف رصيد منخفض لأول أسبوعين.
